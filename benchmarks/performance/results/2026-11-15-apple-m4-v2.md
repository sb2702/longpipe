# Apple M4 MacBook Pro, Chrome 157, 2026-11-15 (v2: model × engine × pipeline)

Background replacement on the 360p and 720p `woman_on_video_call` clip (192
frames), comparing MediaPipe's selfie model on three engines (MediaPipe Tasks,
LiteRT.js, Longpipe) and Longpipe's model with the network on every frame and as
the SDK ships it. Methodology, including what the as-shipped pipeline runs on
each frame and the output-path investigation:
[`../../METHODOLOGY.md`](../../METHODOLOGY.md#performance). This run supersedes an
earlier first run (since removed); see "Changes from the first run" below.

Files (unedited output of `npm run bench`):

- `2026-11-15-apple-m4-v2-session1.json`, `…-session2.json`: transcode, all 37
  pipelines, 360p + 720p, 5 interleaved rounds each (session 1: 23:18–23:38 UTC;
  session 2: 00:08–00:28 UTC).
- `…-diagnostics.json`: process and model-only modes, 3 rounds (23:38–00:03 UTC).
- `…-direct-output.json`: transcode with the old output path (canvas frame
  straight to the encoder), 12 pipelines, 3 rounds (00:03–00:08 UTC).
- `…-output-path.json`: the output-path investigation (`tools/ceiling.mjs`).

## Conditions

- MacBook Pro 14" (Mac16,1), Apple M4, 16 GB, macOS 26.5.1, on AC power, battery
  full, Low Power Mode off; no thermal or performance warning recorded by
  `pmset -g therm` at the start or end of any session.
- Chrome 157.0.8103.51, headless, driven over SSH by Playwright; WebGPU adapter
  `apple metal-3`; WebGL `ANGLE Metal Renderer: Apple M4`; cross-origin isolated.
- Builds: `longpipe@0.0.17` from npm (rows 3, 4); the SDK's `Renderer` compiled
  from `src/` at the 0.0.17 release commit (row 5; `src/` unmodified, recorded
  as `sdkSource`); `@mediapipe/tasks-vision` 1.1.1; `@litertjs/core` 2.5.3;
  `webcodecs-utils` 0.2.6; Vite 8.3.2; Playwright 1.64.1.
- **Not a quiet machine.** The M4 is also a production worker for an unrelated
  GPU service (the paid upscaler). Its jobs were logged once a second; the
  harness discarded and repeated every measurement whose timed pass overlapped a
  job (1 in session 1, 0 in session 2, 7 in the diagnostics), and a post-hoc
  check of the independent log found no accepted transcode measurement within
  1 s of a job. Seven accepted diagnostic (process-mode) passes ended 0.1–1.5 s
  before the second a job was first logged; with 1 s sampling they may have
  overlapped its start by <1 s. Also running throughout: a screen-recording app
  (Screen Studio) with the camera and a VideoToolbox encoder session open, a game
  launcher, a Chrome window; WindowServer used ~30% of the GPU with no benchmark
  running, and the load average was 3.4–5.2. These were not closed (it is
  someone's working machine). Absolute numbers would likely be higher on an idle
  machine; model-only times, for example, were 27–43% higher for MediaPipe
  Tasks and 18% higher for Longpipe xs (WebGPU f16) than in the first run ~3.5
  hours earlier.
- Transcode output path: the **readback stage** (each frame `copyTo()` CPU RGBA,
  then encoded), the same for every pipeline. Without it, canvas frames are
  capped at ~75–110 fps (table at the end).

## Observations

Orderings below hold in both sessions unless stated; the two sessions agree
within 7.5% for every pipeline (median vs median).

- **The fastest model pipeline tested is MediaPipe's model on LiteRT.js
  (WebGPU)**, not Longpipe: 380–414 fps at 360p and 196–204 fps at 720p, against
  288–308 / 155–162 for Longpipe's fastest (xs and small, as shipped, WebGPU).
  Model-only, LiteRT runs it in 0.8–1.05 ms vs 1.6 ms for Longpipe xs's network.
  (MediaPipe's model has lower P3M accuracy and a 256×256 / 256×144 mask; this is
  a speed comparison only.)
- **Same model (MediaPipe selfie), three engines**: LiteRT.js WebGPU is 1.8
  to 2.0× faster than Longpipe's engine on WebGPU (360p, square model: 380–381
  vs 192–206 fps; 1.05 vs 2.70 ms model-only), which is in turn ~1.7× faster
  than MediaPipe Tasks' GPU delegate (114–118 fps). On WebGL2, Longpipe's engine is level with Tasks' GPU
  delegate (122–125 vs 114–123 fps). MediaPipe Tasks' fastest configuration is
  again its CPU delegate with the landscape model (150–153 fps at 360p).
- **Longpipe as shipped vs MediaPipe Tasks** (both are what a user of each SDK
  gets): on WebGPU, xs, small and medium are faster than every Tasks
  configuration at both resolutions (360p: 237–308 vs ≤153; 720p: 140–162 vs
  ≤97). large is level with Tasks' best at 360p (150–157 vs 150–153) and faster at
  720p (104–108 vs ≤97). **xl is slower than Tasks** at 360p (88–91 vs 114–153)
  and at 720p (69 vs 81–97; level with the CPU square model's 69–70). On WebGL2,
  xs and small are faster than Tasks (360p 189–205), medium is level with Tasks'
  best (154–159 vs 150–153; faster at 720p), **large is slower than every Tasks
  configuration at 360p** (101–102) and xl is the slowest pipeline tested.
- **As shipped vs network on every frame** (same f16 precision): the shipped
  schedule is only slightly faster for xs, small and medium on WebGPU (+3–13%
  at 360p, +3–7% at 720p; on WebGL2 +0–14%):
  their off frames are not free, they run the learned flow network, two warps
  and the stabiliser, and for xs the off-frame work costs nearly as much
  as the network (process mode: 331 vs 328 fps). For **large and xl the shipped
  pipeline is 18–27% slower** than the network alone, because they run the flow
  network in addition to the full network on every frame. Temporal quality, which
  is what the flow path is for, is not measured here.
- **Precision**: large and xl run f16 as shipped (see METHODOLOGY). With the
  network every frame on WebGPU, f16 is 23–25% faster than f32 for large (199–203
  vs 162 fps at 360p) and 45–48% for xl (119–121 vs 82). The first run measured
  them in f32.
- **720p is close to the output-path ceiling** for the fastest pipelines: the
  readback stage alone (WebGPU canvas copy) reaches only 224–228 fps at 720p,
  so differences between the fast pipelines are compressed there; 360p separates
  them better.
- **Without the readback stage** (old path, table below), every pipeline lands at
  73–110 fps and the no-model WebGPU canvas copy (92–95 fps) is slower than
  LiteRT or Longpipe xs (98–110): the encoder's handling of canvas frames, not
  the effect, sets the number. This is what compressed the first run.

- **Output path**: readback stage instead of canvas frame → encoder (the first
  run's transcode numbers were capped by the encoder's canvas-frame path).
- **Precision**: large and xl in f16 (as `EffectsPipeline` runs them by default),
  with f32 rows kept for comparison; the first run used f32.
- **New rows**: LiteRT.js (row 2), MediaPipe model on Longpipe's engine (row 3),
  Longpipe as shipped (row 5).
- **Protocol**: interleaved rounds with each pipeline recreated per round,
  instead of each pipeline's runs back to back; measurements overlapping worker
  jobs discarded automatically.
- **Fix**: the WebGL2 canvas-copy row composited all-green (incomplete alpha
  texture) in the first run; it now copies the frame. Its cost was the same shader
  work either way.
- `longpipe` 0.0.17 (was 0.0.16; no change to the Longpipe networks or ops
  used by rows 4–5 beyond what 0.0.17 shipped).
