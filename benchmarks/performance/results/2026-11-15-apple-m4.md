(`@mediapipe/tasks-vision` 1.1.1), background replacement on the 360p and 720p

[`../../METHODOLOGY.md`](../../METHODOLOGY.md#performance).

## Observations

- **End-to-end transcode FPS is bounded by the output path on this machine.**
  Turning a canvas-rendered frame into an H.264 `VideoEncoder` input costs
  ~6–10 ms per frame here: the canvas-copy pipelines (no model at all) reach only
  97–159 fps, against 400–1,150 fps for passthrough (decoded frames straight to
  the encoder). Most effect pipelines land in the same 70–150 fps band, so
  transcode FPS compresses the differences between them, and its absolute value
  moved by up to ~50% between sessions (canvas copy WebGPU: 99 vs 154 fps at
  360p). The same harness design run from the webrtcHacks repo on this machine
  today gave its WebGPU pipeline 133 fps, vs 358 fps published with Chrome 156
  in October, so this looks like a Chrome 157 / macOS change rather than
  anything specific to these pipelines. Not explained further.
- **Process FPS and model ms separate the pipelines and keep their order across
  sessions**, though absolute process FPS was ~25% lower in session 2 for every
  pipeline, passthrough included.
- **Longpipe WebGPU xs, small, medium and large are faster than every MediaPipe
  configuration** in process mode in both sessions (360p, session 1: 449 / 421 /
  336 / 236 fps vs MediaPipe's best, CPU landscape, 209), and at or above
  MediaPipe in transcode. large vs MediaPipe CPU landscape is close in session 2
  (185 vs 180 fps).
- **Longpipe xl is slower than every MediaPipe configuration** in process mode
  (108 fps vs 151–209 at 360p) and in 720p transcode. Its 1280×768 network costs
  8.3 ms (360p) to 15.7 ms (720p input) on WebGPU.
- **On WebGL2, Longpipe is slower than on WebGPU**, and only xs and small are
  clearly faster than MediaPipe in process mode (284 / 275 vs 209 fps, session 1).
  medium is level with MediaPipe CPU landscape (219 vs 209; 183 vs 180), large
  is slower than it (177 vs 209; 145 vs 180) and level with MediaPipe GPU, and xl
  is the slowest pipeline tested. In session 1's transcode, every Longpipe WebGL
  preset was below MediaPipe GPU (70–77 vs 83–86 fps at 360p); in session 2,
  xs/small were above it (110 vs 104).
- **MediaPipe's fastest configuration here is the CPU (WASM) delegate with the
  landscape model** (3.2 ms model, 209 fps process at 360p), not the GPU
  delegate. The square model costs it ~50% more on the CPU.
- Longpipe's model-only time grows with the input frame (xs: 1.38 ms at 360p,
  2.18 ms at 720p) because the `Input` op samples the full frame; MediaPipe's
  grows more (it upsamples its mask to frame size inside `segmentForVideo`).
- Longpipe here runs the network on every frame. The production
  `EffectsPipeline` runs xs on every 3rd frame and small/medium on every 2nd, so
  its per-frame model cost for those presets is lower than shown; it also adds
  the optical-flow stabiliser, which costs extra. Neither is measured here.
